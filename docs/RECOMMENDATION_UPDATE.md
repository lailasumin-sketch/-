## 기존 프로젝트 분석

- 추천 버튼: `public/app.js`의 `#trip-form` submit → `recommend()` → `buildTrip()`.
- 문장 입력: `parsePrompt()`의 키워드 추출 후 동일한 `recommend()` 사용. AI 호출이 아님.
- 웹 데이터: `public/catalogue.json` 관광 조사 후보 35곳, `public/dining.json` 가상 맛집 18곳·카페 12곳. `events.json`의 확인된 행사는 현재 없음.

- 이전 로직은 10시 시작, 고정 종료시간, 자가용 25분·대중교통 45분의 임의 이동 여유를 사용. 별도의 구간·권역별 이동시간표, 좌표·도로 데이터는 없었음.

## 구현된 기능

- 시작시간과 전체 활동 가능시간 입력. 여행 기간이 여러 날이면 총 분을 일수로 나누고 남은 분은 앞 날짜부터 1분씩 배분.
- 매일 같은 시작시간, 첫 방문지 도착 기준. 일자 간 이동·숙박·수면은 별도 안내이며 시간표에 임의 체크인을 넣지 않음.
- 실제 후보의 체류시간을 유지하며 종료시간·영업시간에 맞지 않는 방문은 제외. 빈 일정을 검색 과제로 채우지 않음.
- 알려진 운영시간, 요일 휴무, 브레이크타임을 검사. 필요한 대기·휴식도 별도 구간으로 계산. 미확인 운영시간·휴무는 확인 필요 표시.
- 음식점은 가능한 경우 11:30~14:00에 시작하도록 선호. 카페는 관광 방문 전후 배치 선호. 같은 날짜의 식사·카페는 각각 1곳으로 제한해 유형을 분산.
- 같은 장소와 같은 시설군은 전체 여행에 중복 배치하지 않음.
- 동행·관심사·예산·주차·반려견·실내외 등 기존 데이터가 있는 필터 유지. 자연·힐링은 장소 이름·실내외 분류에 따른 편집상 취향 점수이며 공식 태그가 아님.
- 방문/이동/대기 시작·종료, 분류·이유·체류시간·이동 근거·읍면·가상/검증 상태 표시.
- 총 방문 수·체류시간·이동시간·지역 상권 연계 장소 표시. 음식점·카페·특산물 쇼핑 분류의 실제 선택된 레코드만 세며, 가상·조사 후보·원문 확인을 분리.
- CSV 기반 웹 JSON이 없거나 손상되면 해당 업소만 제외하고 관광 기능 유지. 필수 관광 JSON 실패는 명시적 오류.

## CSV 및 JSON 필드 사용

| CSV 필드 | 변환·사용 |
|---|---|
| 업소ID, 업소명(가상), 분류 | id, name, category/categories: 중복 방지·관심사·가상 상태·상권 집계 |
| 가상 배치 권역 | area 및 region: 가상 읍면 표시·권역 필터. 실제 주소나 이동시간이 아님 |
| 세부분류, 대표메뉴(가상), 추천태그 | cuisine/menu/tags: 기존 키워드 검색·업소 설명 |
| 1인예산(원·가정) | price: 업소별 1인 상한 필터. 전체 여행 경비 계산이 아님 |
| 추천 동행, 분위기 | audiences/atmosphere: 동행 적합성 및 설명 |
| 체류시간(분·가정) | minutes: 방문 종료시간·체류 합계. 시간을 줄여 억지로 맞추지 않음 |
| 오픈(가정), 마감(가정) | openTime/closeTime: 방문 전체가 영업시간 안에 들어가는지 확인 |
| 정기휴무(가정), 브레이크타임(가정) | closedWeekdays/breakTime: 날짜별 휴무 제외·대기 및 방문 시간 조정 |
| 반려견(가정), 주차(가정), 소음정도(가정), 공간(가정) | petPolicy/parking/noise/space: 기존 조건 필터 |
| 예약정책(가정), 데이터구분 | 예약 관련 표시·가상 여부 검증. 예약 API 없음 |

주소·전화·예약URL은 원본의 실정보 없음 상태를 유지하며 실제 연결을 생성하지 않습니다. 관광 JSON의 id/name/categories/region/group/audiences/minutes/indoor/hold/verification 및 가능한 openingHours/closedWeekdays/area를 재사용합니다.

운영시간 JSON 스키마는 `openTime`, `closeTime`, `breakTime: ["12:00","13:00"]` 또는 `openingHours: {open, close, breaks: [[...]], closedWeekdays}`를 지원합니다. 운영시간이 모두 없으면 확인 필요, 일부만 있거나 잘못된 시각이면 방문 배치에서 제외합니다. 자정을 넘기는 영업은 현재 지원하지 않습니다.

## 일정 계산 방식

1. 입력·일수·전체 분·자정 초과를 검증하고 조건에 맞는 후보를 준비합니다.
2. 같은 날짜는 한 권역에서 구성합니다. 권역별로 후보 순서와 영업시간 슬롯을 탐색하고 상위 32개 경로를 유지합니다. 전역 최적해를 보장하는 최단 경로 알고리즘은 아닙니다.
3. 후보별 `도착 최소 시각 = 직전 종료 + 등록/입력 이동분`, `방문 시작 = 도착과 오픈 중 늦은 시각`, `방문 종료 = 시작 + 체류분`을 계산합니다. 브레이크타임과 겹치면 끝난 뒤로 이동하고 그 대기도 예산에 포함합니다.
4. 종료시각을 넘기는 후보·휴무·중복·조건 불일치는 버립니다. 관심사 포함 범위와 일치 수 → 동행 적합성 → 알려진 운영시간 → 미확인 이동 구간 수·알려진 이동분 → 점심·카페 배치와 대기를 순서대로 비교합니다. 시간 예산 충족은 모든 후보의 필수 조건입니다.
5. 여행 속도는 날짜별 방문 상한(느긋 4, 보통 6, 활동적 8) 및 관광 방문 상한(반나절/느긋 2, 보통 4, 활동적 6)에 반영합니다. 임의로 체류시간이나 도로 속도를 바꾸지 않습니다.
6. 총 체류·확인 가능한 이동·대기 합계를 계산하며, 방문이 아닌 검색·숙박 문의·대기는 방문 수/상권 수에 넣지 않습니다.

### 이동 데이터와 시간 보장의 범위

현재 `travel-times.json`은 빈 목록입니다. 숫자가 없다는 것은 0분이 아닙니다.

- from/to 또는 권역별 표 + 이동수단 + minutes + basis + source가 주어졌을 때만 사용. 명시한 경우에만 역방향 적용.
- `basis: fictional`은 **가상 이동시간**, published는 **등록된 이동시간(실시간 아님)** 표시.
- 사용자가 선택적으로 입력한 이동 여유는 **사용자 지정 이동 여유**이며 실제·가상 시간표로 둔갑시키지 않음.
- 자료·입력이 없으면 이동 minutes/endTime은 null, 총 이동시간도 미정. 이후 방문시각은 이동을 더하지 않은 **최소 시각의 임시 일정**이며 실제 종료시간을 보장하지 않음. 해당 경고는 상단·구간·복사문 모두 표시.
- 시간 예산 검사는 등록/사용자 입력 값이 있는 구간은 이동까지 포함. 미확인 구간이 있으면 체류·대기와 알려진 이동만 계산한 하한값이므로, 실제 전체 소요가 예산 안이라는 의미가 아님.
- 첫 방문지까지 이동, 날짜 간 이동·숙소 연결은 자료가 없어 별도 확인 필요.

## 실행·빌드

추가 패키지 설치 없이 Node.js 20 이상:

```sh
npm start
# 브라우저: http://localhost:3000
npm test
npm run data:check
npm run build
```

`npm run build`는 자료 일치 검사와 자동 테스트를 수행합니다. 별도 컴파일이 없는 정적 서비스이며 배포 산출물은 `public/`입니다. Vercel은 동일한 build를 실행합니다. CSV를 편집했다면 먼저 `npm run data:dining`으로 JSON을 갱신합니다.

## 미구현·제약

실시간 지도/도로/대중교통 경로, 실제 최신 영업·예약·날씨, 실제 업소 검증, 자동 주소·읍면 보완, 외부 AI, 야간을 넘기는 영업시간, 날짜 간 숙소·이동 연결, 전역 최적 경로는 구현하지 않았습니다. 관광 후보와 가상 업소의 구분은 유지했습니다. 이동 미확정인 경우 실제 전체 종료를 보장하는 것은 주어진 자료만으로 불가능하므로 경고로 명시합니다.
